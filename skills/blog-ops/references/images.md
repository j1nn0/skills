# 図とスクリーンショット

図は本文の代わりではなく、文章では追いにくい関係を見せるために置く。
置き場所とパスの規約は `references/new-post.md` にある。ここでは何を作るかと、どう仕上げるかを決める。

## 入れるかどうか

入れる価値があるもの。

- 3つ以上のコンポーネントが関わる構成や、リクエストがどこを通るかの流れ
- 時系列(障害のタイムライン、リトライやハンドオフの順序)
- 数値の比較。表で足りるなら表でよい。傾向を見せたいときだけグラフにする
- 読者が同じ画面を探す必要がある UI 操作

入れないもの。本文で1文で書けることの図解、装飾目的のイラスト、コードをそのまま画像にしたもの。コードは選択とコピーができる必要があるので、必ずコードブロックで書く。

## 図(Mermaid)

構成図やシーケンス図は Mermaid で書く。テキストなので差分が読め、後から直せる。

- 箱には実際のサービス名、関数名、テーブル名を書く。「サーバー」「DB」のような汎用ラベルは、読者が自分の知識と対応付けられない
- 1枚に詰め込まない。本文の1つの論点に対して1枚にする
- 記事の主張に関係する経路だけ描く。網羅は構成ドキュメントの仕事であって、記事の仕事ではない
- レンダリングは環境依存なので、`hugo server` で実際に表示を確認する。表示できないテーマなら画像に書き出して置く

## スクリーンショット

- 撮る前に、記事に出せない情報(トークン、メールアドレス、社内の識別子、他人の名前)がないか確認する。塗りつぶすより、ダミーの値に差し替えてから撮り直すほうが安全
- 画面全体ではなく、読者が見る必要のある範囲を切り出す。どこを見ればいいか分からない画像は、無いのと変わらない
- 強調が必要なら枠線か矢印を1つだけ足す。UI は変わるので、本文側にも操作の言葉での説明を残す
- 連番で並べるときはファイル名も連番にする(`01-settings.webp`、`02-result.webp`)。後から差し替える人が対応を追える

## 仕上げ

- 形式は webp を既定にする。写真でない UI のスクリーンショットは png でもよい。既存記事の形式に合わせる
- 横幅は記事の本文幅の2倍程度(1600px 前後)まで。それ以上は読者の転送量が増えるだけで、見え方は変わらない
- 1枚あたり数百 KB を超えるなら、解像度か形式を見直す
- ファイル名は小文字ハイフン区切りで、内容が分かる名前にする

## alt テキスト

alt はファイル名の言い換えではなく、その画像から読者が受け取るはずの情報を日本語で書く。読み上げ環境と、画像が表示されなかったときの読者がこれを頼りにする。

```markdown
![設定画面でプラグインを有効化している様子](/images/my-post/01-settings.webp)
```

- 図なら、何と何がどうつながっているかを書く。「アーキテクチャ図」だけでは何も伝わらない
- グラフなら、読み取ってほしい傾向を書く。「p99 が 340ms から 45ms へ下がった推移」
- 装飾目的の画像は alt を空にする(`![](...)`)。読み上げが不要な内容を読むのを避けられる

## 確認

- [ ] 画像が `static/images/<slug>/` にあり、本文から `/images/<slug>/...` で参照している(`check_posts.py` が実在を検査する)
- [ ] alt が画像の内容を説明している
- [ ] 秘匿情報が写り込んでいない
- [ ] Mermaid が `hugo server` で表示できる
- [ ] ダークモードがあるテーマなら、両方で図が読める
