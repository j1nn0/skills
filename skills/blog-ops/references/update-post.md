# 公開済み記事の改訂

公開済みの記事は、読者がブックマークし、他所からリンクされ、検索結果に載っている状態にある。
新規記事と違って、変更が既存の読者に影響する。まず「どの種類の改訂か」を決めてから手を動かす。

## 改訂の種類を決める

| 種類 | 例 | 扱い |
|------|----|------|
| 誤りの訂正 | 事実誤認、動かないコード、誤ったバージョン記述 | すぐ直す。影響が大きければ訂正を明示する |
| 陳腐化の更新 | 価格改定、API の変更、非推奨化、UI の変更 | 一次情報で確認してから直す |
| 追記 | 後日分かったこと、続報、読者からの指摘 | 本文に溶かすか、追記節にするかを選ぶ |
| 加筆・書き直し | 説明の不足、構成の作り直し | 実質的に新規執筆。執筆スキルの工程に戻す |
| 撤回 | 前提が崩れて記事全体が成り立たない | 削除ではなく、何が変わったかを書いて残す方が読者の役に立つ |

事実に関わる改訂は `fact-check-ja` で一次情報に当たってから直す。記憶で直すと、古い記述を別の古い記述に置き換えることになる。

## 訂正を明示するか、黙って直すか

判断の基準は、その記事を読んで行動した読者がいるかどうかである。

**黙って直してよい** — 誤字、表現の改善、リンク切れの張り替え、読者の判断を変えない補足。

**訂正を明示する** — 手順どおりにやると失敗する記述、誤った数値、逆の結論につながる記述、セキュリティや課金に関わる誤り。読者は自分が過去に読んだ内容が変わったことを知る必要がある。

明示するときは、消した記述を読者が追えるようにする。

```markdown
> **2026-08-05 追記**
> 公開時点では〜と書いていたが、これは誤りだった。vN.N.N では〜になる。
> 該当箇所を修正した。
```

元の記述を跡形なく消すと、その記事を根拠に判断した読者が何が変わったのか分からない。誤りの大きさに応じて、消すか、取り消し線で残すか、追記で説明するかを選ぶ。

## 日付の扱い

- `date` は公開日である。改訂で書き換えない。書き換えると記事一覧と RSS の順序が変わり、既存の読者に新着として再配信される
- 改訂日は `lastmod` に書く。テーマが表示に対応していれば読者に更新が伝わり、対応していなくてもサイトマップに反映される
- 実質的に別記事になるほど書き直したなら、改訂ではなく新規記事にして、旧記事から新記事へリンクする方を検討する

```yaml
date: 2026-03-01
lastmod: 2026-08-05
```

`check_posts.py` は `lastmod` の形式と、`date` より前になっていないかを検査する。

## スラッグとタグを変えるとき

URL は公開後の契約である。改訂のついでに変えない。

変える必要があると判断したら、`references/publish-check.md` の「URL に影響する変更」と `references/tags.md` の手順に従う。新旧 URL の一覧とリダイレクトの要否をユーザーに報告してから進める。

## 改訂後の確認

- [ ] `fact-check-ja` の確認カード、または一次情報の URL とバージョンが残っている
- [ ] `date` を書き換えていない。改訂日は `lastmod` にある
- [ ] 訂正の明示が必要な変更なら、追記か取り消し線で読者が追える
- [ ] 本文中の内部リンクと画像パスが生きている(`check_posts.py`)
- [ ] `hugo --minify` が通る
- [ ] 記事内の「〜時点では」という時点表記が、今回の改訂内容と矛盾していない
