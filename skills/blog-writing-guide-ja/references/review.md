# 下書きのレビュー・編集

大規模なリライトでは、詳細を読み直す前に見出しと各段落の先頭文だけを順に読む。
それだけで論旨が追えるか、同じ構成や書き出しを繰り返していないか、節ごとの厚みに意図した差があるかを確かめる。
見出しと直後の段落冒頭が同じ主張の言い換えだけになっていないかも確かめ、本文では理由や具体へ進める。
この確認のために、すべての見出しや段落を同じ型へそろえない。

## チェックリスト

3つのリストの全項目を、通ったか、直したか、理由を添えて残したかに仕分ける。全項目の仕分けが済んだ時点でレビューを終える。

■技術レビュー

- [ ] 技術的な主張がすべて正確か
- [ ] コードサンプルが動くか
- [ ] アーキテクチャの説明が実態と一致しているか
- [ ] 数字とベンチマークが正しいか
- [ ] 専門家が読んで顔をしかめる過度な単純化がないか

この4項目は読んだ印象では判定できない。`fact-check-ja` がある環境では、一次情報への当たり方と未確認だったときの書き方をそちらに任せる。ない環境では、数値、バージョン依存の挙動、「できない」という断定、他ツールとの比較を優先して公式ドキュメントに当たり、確認できなかった主張は削らずに、書き手が持っている根拠の範囲まで狭めて書く。

■編集レビュー

- [ ] 書き出し2〜3文で読者を掴んでいるか
- [ ] 「共有されるか」テストを通るか
- [ ] 企業広報調の言い回し、埋め草、水増しがないか
- [ ] 見出しが情報を運んでいるか
- [ ] 長さが適切か（SKILL.md「長さの目安」の範囲。外れているなら理由を説明できるか）
- [ ] タイトルが具体的で手を止めさせるか

■最終チェック

- [ ] ドキュメントやリポジトリへのリンクがあるか
- [ ] changelog の焼き直しになっていないか
- [ ] 記事内で繰り返される数・固有名・時系列が、全箇所で一致しているか
- [ ] 「この記事で分かること」と見出しの並びが、本文の内容と対応しているか
- [ ] 文レベルの仕上げ確認を適用したか（`writing-ja` があればその手順を使う）

数と固有名は、front matter の `summary`、導入、見出し、本文、まとめに散らばる。1箇所を直したら、その値で記事全体を検索して残りを潰す。「4種類」と直したのに見出しが「5つの観点」のまま、という取りこぼしはここで防ぐ。

これは記事内で辻褄が合っているかの確認であり、その数が事実として正しいかの確認ではない。両方いる。外部の一次情報と突き合わせるのは技術レビューの側で、`fact-check-ja` の担当になる。

## 返し方

指摘は、直さないと記事の主張・正確さ・読者の理解を損なうものと、よりよくするための提案に分ける。弱い箇所を並べるだけで終わらせず、必ず引用、問題の説明、書き直し例をセットにする。

### 必ず直す

技術的な誤り、主張と根拠の不一致、読者が誤解する構成、本文にない事実の追加が該当する。

```md
> 引用: 「…」

問題: [何が事実と合わないか、またはなぜ判断できないか]
書き直し例: 「…」
```

### 提案

主張は正しいが、導入、見出し、説明順、具体性、文体を改善できる箇所が該当する。依頼範囲と書き手の声を尊重し、採用を強制しない。

```md
> 引用: 「…」

提案: [読み手にとっての改善点]
書き直し例: 「…」
```
